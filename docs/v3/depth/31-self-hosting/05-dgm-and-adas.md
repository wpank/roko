## 1. The Godel Machine

Schmidhuber's original Godel Machine (2003) proposed a fully self-referential
system that provably improves itself: before applying any self-modification,
the system constructs a formal proof that the modification will improve its
future performance. The proof is verified by a trusted proof checker that is
itself outside the modifiable surface.

The Godel Machine is elegant but impractical. Constructing formal proofs of
improvement for non-trivial software systems is computationally intractable.
No production system has ever implemented a Godel Machine.

---

## 2. Darwin Godel Machine (DGM)

The Darwin Godel Machine (Zhang et al. 2025, arXiv:2505.22954) replaces
formal proofs with empirical evaluation, and single-point modification with
population-based evolution.

### 2.1 Core Mechanism

```
Archive of past solutions (growing population)
    |
    v
Generate candidate self-modifications
(mutations of successful past architectures)
    |
    v
Evaluate candidates on benchmark tasks
(empirical, not provable)
    |
    v
Select: keep candidates that improve over the archive
(archive-based selection pressure)
    |
    v
Add winners to archive; iterate
```

DGM maintains a growing archive of agent architectures. New candidates are
generated by mutating successful past architectures (analogous to biological
evolution). Selection is empirical: candidates that outperform the archive on
a benchmark suite are added; others are discarded.

### 2.2 Key Differences from Godel Machine

| Property | Godel Machine | Darwin Godel Machine |
|---|---|---|
| Proof of improvement | Formal proof required | Empirical evaluation sufficient |
| Modification type | Single-point | Population-based evolution |
| Archive | Not applicable | Growing archive of architectures |
| Selection | Proof verification | Benchmark comparison |
| Tractability | Intractable for real systems | Feasible but computationally expensive |

### 2.3 Roko Analogues

DGM's components map to existing Roko subsystems:

| DGM Component | Roko Analogue | Status |
|---|---|---|
| Archive of solutions | Episode log (`.roko/episodes.jsonl`) + skill library + playbook store | Wired |
| Candidate generation | Prompt experiment variants (ExperimentStore) | Wired |
| Empirical evaluation | Per-task verify commands (the 19-gate pipeline runs only in tests) + 4 key metrics | Partial |
| Selection pressure | UCB1/Thompson bandit algorithms | Wired |
| Population management | Experiment archival with significance tests | Wired |
| Open-ended evolution | ADAS-style architecture search | Not implemented |

Roko already implements DGM's pattern at the **deployment behavior** level:
prompt variants are the "candidate mutations," the gate pipeline is the
"benchmark evaluation," and bandit selection is the "archive-based selection
pressure." What Roko does not implement is DGM's open-ended quality: the
mutations are confined to prompt content, not to system architecture.

## 3. ADAS: Automated Design of Agentic Systems

ADAS (Hu et al. ICLR 2025) brings DGM-style evolution to agent system
architecture. Instead of evolving neural network weights, ADAS evolves the
**scaffolding code** -- agent roles, communication patterns, tool
configurations, and routing strategies.

### 3.1 Results

- +14% accuracy on ARC (Abstraction and Reasoning Corpus)
- +13.6 F1 improvement on reading comprehension tasks
- Discovered novel agent architectures that outperformed expert-designed baselines

### 3.2 ADAS Search Space

ADAS operates on five dimensions:

| Dimension | What Varies | Roko Configuration |
|---|---|---|
| Agent roles | How many agents, what capabilities | `roko.toml` agent definitions |
| Communication | Sequential, parallel, hierarchical | Graph topology |
| Tool selection | Which tools per role | `AgentContract` tool policy |
| Prompt templates | Structure, content, ordering | `SystemPromptBuilder` templates |
| Routing strategies | Model selection rules | `CascadeRouter` configuration |

### 3.3 Roko's ADAS Pathway

Roko has all the components needed for ADAS:

1. **Architecture representation in code:** `roko.toml` configuration +
   `SystemPromptBuilder` templates + Graph TOML definitions
2. **Evaluation harness:** deterministic verification by each task's authored
   `verify` commands (the 19-gate pipeline runs only in tests)
3. **Performance metrics:** C-Factor, 4 key metrics, regression detection
4. **Experiment framework:** `ExperimentStore` for A/B testing
5. **Search strategy:** Cascade router bandits (extensible to architecture)

What is **missing** is the meta-agent that operates on these components:

```
ADAS Meta-Agent (not implemented)
    |
    +-- Reads: roko.toml, graph definitions, prompt templates
    +-- Generates: variant configurations (mutations)
    +-- Evaluates: runs plans with variant configs through gate pipeline
    +-- Selects: promotes winning configurations
    +-- Deploys: updates production configuration
    |
    v
Requires: human approval gate (L4 structural adaptation)
```

### 3.4 Why ADAS Is Not Automated

ADAS-level modification is deliberately not automated in Roko because:

1. **Non-widening authority (R04):** Meta-agent lifecycle enforces that
   spawned agents cannot acquire wider capabilities than their parent. An
   ADAS meta-agent that modifies the capability system would violate this
   invariant.

2. **Constitutional constraints:** The safety constitution forbids self-
   modification of `roko-gate` and `roko-agent/safety`. ADAS operating on
   graph topology could indirectly modify verification behavior.

3. **Gate gaming risk:** A system that evolves its own architecture while
   evaluated by its own gates has a strong gradient toward gaming the gates
   rather than genuinely improving. The external evaluator requirement
   (Huang et al. ICLR 2024) is violated when the system under evaluation
   controls the evaluator.

4. **Appropriate for development tools:** A tool that modifies production
   codebases should not autonomously restructure its own verification
   pipeline. The cost of a false positive (a self-modification that appears
   beneficial but introduces subtle bugs) is borne by the user's production
   code, not by the system itself.

## 4. AI4AI-Bench: Can AI Improve Its Own Learning Algorithms?

AI4AI-Bench (Chi et al. 2026, arXiv:2608.20318) provides the first
systematic benchmark for evaluating whether AI systems can improve their own
learning algorithms. This directly measures the capability that ADAS and DGM
require but leave implicit.

### 4.1 Three Capability Levels

| Level | Capability | Test |
|---|---|---|
| 1. Understanding | Can the system correctly analyze learning code? | Read learning algorithm source, answer questions about its behavior |
| 2. Debugging | Can the system fix bugs in learning algorithms? | Given a buggy learning algorithm, identify and fix the bug |
| 3. Improvement | Can the system improve a learning algorithm? | Propose a modification that improves held-out performance |

### 4.2 Roko's Position

**Level 1 (Understanding):** Operational. Roko agents successfully read,
understand, and modify `roko-learn` source code during plan execution. The
48 accepted epics include modifications to the learning subsystem itself.

**Level 2 (Debugging):** Operational. When gate failures occur in learning
code, the replan controller provides enriched context (error signatures,
compile errors, test failures) that enables the agent to diagnose and fix
the bug. The gate pipeline provides ground-truth feedback.

**Level 3 (Improvement):** Bounded. Prompt experiments and cascade routing
demonstrate empirical improvement. But structural improvements to the learning
algorithm itself (e.g., "change the confidence dynamics formula") require
human review via L4 structural adaptation. The system can propose such
changes but cannot autonomously deploy them.

### 4.3 Key Insight: Controlled Experiments

AI4AI-Bench's central insight is that improvement claims require controlled
experiments. Without a holdout group, apparent improvements may be noise,
regression to the mean, or artifacts of changing task distributions.

Roko's `ExperimentStore` implements this: each experiment assigns tasks to
treatment (current learning config) and control (frozen baseline) groups
using hash-based assignment (`hash(task_id) % 100 < treatment_pct`). The
default split is 80% treatment, 20% holdout. Experiments conclude only when:

- Minimum samples (50 per variant) are collected
- Significance threshold (p < 0.05) is reached
- Effect size (delta > 5%) is meaningful
- Variance Inequality check confirms the leader cannot be overtaken

## 5. Structural Adaptation Limits

L4 structural adaptation is Roko's interface to ADAS-level improvement. It
is explicitly human-gated:

### 5.1 What L4 Can Propose

- New model additions to the cascade router
- Graph topology changes (new cell types, new edges)
- Cell registration changes (new cell implementations)
- Plugin additions or capability grants
- Routing strategy modifications

### 5.2 What L4 Cannot Do

- Disable or weaken gates (constitutional constraint)
- Modify safety modules (constitutional constraint)
- Grant capabilities beyond the parent's authority (R04 non-widening)
- Deploy without human approval (L4 is explicitly manual)

### 5.3 R04: Meta-Agent Lifecycle

R04 delivers bounded meta-agent lifecycle with:

- Owner-scoped durable proposal/activation/morph/rollback/deactivation
- Non-widening authority enforcement (tools, data, network, cost, spawn,
  expiry, depth, fan-out, retry, lineage-cost bounds)
- Exact five-head corrigibility evidence per activation
- Single-use artifact-bound R03 acceptance (arena-verified qualification)

R04 provides the *machinery* for ADAS-level adaptation but does not close
the loop: every activation requires explicit human approval.

## 6. The Self-Improvement Ceiling

Three factors define the ceiling of Roko's self-improvement:

1. **External verifier floor:** The gate pipeline provides the ground-truth
   signal. The gates themselves do not improve (no automatic addition of new
   test cases, no new lint rules). This creates a ceiling: the system can
   improve up to the quality level that the existing gates can detect, but
   not beyond.

2. **Constitutional boundary:** The safety constitution is immutable to the
   learning system. This is a hard boundary, not a soft one -- no amount of
   improvement within the bounded self-refinement class can cross it.

3. **Human bandwidth:** L4 structural adaptation is gated by human approval.
   The rate of structural improvement is limited by the human's review
   bandwidth.

These three ceilings are by design. A development tool should have clear,
well-defined limits on its self-modification capability. The alternative --
unbounded self-modification -- is the DGM/ADAS class, which trades safety for
expressiveness in ways that are inappropriate for systems modifying production
code.
