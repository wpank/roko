# Language Providers

> **Parent:** [34-CODE-INTELLIGENCE](../../34-CODE-INTELLIGENCE.md) Sections 4, 5

## Overview

Code intelligence is language-agnostic at the `roko-index` level. All
language-specific knowledge is encapsulated in `LanguageProvider`
implementations. Three providers ship today:

| Crate | Language | Lines | Tests | Parsing approach |
|-------|----------|-------|-------|-----------------|
| `roko-lang-rust` | Rust | 1,387 | 46 | Heuristic + feature-gated tree-sitter |
| `roko-lang-typescript` | TypeScript/JS | 939 | 33 | Heuristic |
| `roko-lang-go` | Go | 672 | 25 | Heuristic |

Each crate implements the `LanguageProvider` trait from `roko-core` and
optionally provides a `BuildSystem` implementation for detecting project
structure.

## Rust Provider: `roko-lang-rust`

### Heuristic parser (902 lines, 39 tests)

The `RustLanguageProvider` implements line-by-line heuristic parsing:

**Import parsing** extracts three forms:
- `use path::to::Item;` (with brace expansion: `use path::{A, B}`)
- `mod name;` (module declarations)
- `extern crate name;`

**Symbol extraction** recognizes:
- Functions: `fn`, `async fn`, `unsafe fn`, `const fn`, `pub fn`,
  `pub(crate) fn`
- Structs: `struct Name`
- Enums: `enum Name`
- Traits: `trait Name`
- Impls: `impl Name`, `impl Trait for Type`
- Constants: `const NAME`
- Type aliases: `type Name`
- Modules: `mod name`

**Visibility handling** parses `pub`, `pub(crate)`, and `pub(super)`
prefixes. Angle bracket skipping handles generic type parameters in
function signatures (e.g., `fn process<T: Display>(x: T)`) to correctly
extract the function name.

**Build system**: `CargoBuildSystem` detects Cargo workspaces, parses
`Cargo.toml` for workspace members, and identifies build targets.

**Known limitations**:
- Cannot parse nested function definitions (closures, inner functions)
- Cannot parse items generated by procedural macros
- Multi-line function signatures where `fn` and the name are on different
  lines
- `#[cfg]`-gated items are always included regardless of feature flags
- Attribute macros that transform item syntax

### Tree-sitter parser (485 lines, 7 tests)

The `TreeSitterRustProvider` in `tree_sitter_parser.rs` provides
AST-accurate parsing behind the `tree-sitter` feature flag:

```rust
pub struct TreeSitterRustProvider;

impl LanguageProvider for TreeSitterRustProvider {
    fn language_name(&self) -> &str { "rust" }
    fn file_extensions(&self) -> &[&str] { &["rs"] }

    fn parse_imports(&self, source: &str) -> Vec<Import> {
        let Some(tree) = parse_source(source) else { return Vec::new() };
        let mut imports = Vec::new();
        collect_imports(tree.root_node(), source, &mut imports);
        imports
    }

    fn extract_symbols(&self, source: &str) -> Vec<Symbol> {
        let Some(tree) = parse_source(source) else { return Vec::new() };
        let mut symbols = Vec::new();
        collect_symbols(tree.root_node(), source, &mut symbols);
        symbols
    }
}
```

**Advantages over heuristic parsing**:
- Handles nested definitions, multi-line signatures, and macro-expanded
  code
- Scope-aware symbol extraction via AST traversal
- Impl block methods extracted via recursive `collect_impl_methods()`
- Graceful error recovery (parse errors do not prevent extraction)
- Column-level source locations (exact byte offsets)

**Node types traversed**:
- `function_item` for function definitions
- `struct_item` for struct definitions
- `enum_item` for enum definitions
- `trait_item` for trait definitions
- `impl_item` for impl blocks (with trait name extraction)
- `const_item` and `static_item` for constants
- `type_item` for type aliases
- `mod_item` for module definitions
- `use_declaration` for imports (including brace groups)

A parity test verifies that tree-sitter extracts at least as many symbols
as the heuristic parser for standard Rust source.

## TypeScript Provider: `roko-lang-typescript`

### Parser (939 lines, 33 tests)

The `TypeScriptLanguageProvider` handles both TypeScript and JavaScript:

**Import parsing** extracts:
- ES module imports: `import { X } from "path"`,
  `import X from "path"`, `import * as X from "path"`
- Type-only imports: `import type { X } from "path"`
- CommonJS requires: `const X = require("path")`

**Symbol extraction** recognizes:
- Functions: `function name(`, `export function name(`,
  `async function name(`
- Classes: `class Name` (mapped to `SymbolKind::Struct`)
- Interfaces: `interface Name` (mapped to `SymbolKind::Trait`)
- Type aliases: `type Name =`
- Constants: `const NAME`, `export const NAME`
- Enums: `enum Name`
- Export defaults: `export default class/function`

**Cross-language mapping**:
- TypeScript `class` maps to `SymbolKind::Struct` (classes = data + methods)
- TypeScript `interface` maps to `SymbolKind::Trait` (interfaces define
  contracts)
- `export` keyword maps to `Visibility::Public`

**Build systems**: `NpmBuildSystem`, `PnpmBuildSystem`, and
`YarnBuildSystem` implementations detect package.json, lockfiles, and
workspace configurations.

**Known limitations**:
- Cannot parse destructured exports
- Cannot distinguish between `const` value declarations and `const enum`
- Template literal expressions in import paths
- Dynamic `import()` calls are not captured
- JSX/TSX component definitions are not recognized as symbols
- Arrow functions assigned to variables are partially detected

## Go Provider: `roko-lang-go`

### Parser (672 lines, 25 tests)

The `GoLanguageProvider` handles Go:

**Import parsing** extracts:
- Single imports: `import "path"`
- Grouped imports: `import (\n\t"path1"\n\t"path2"\n)`
- Aliased imports: `import alias "path"`

**Symbol extraction** recognizes:
- Functions: `func name(` -- distinguished from methods by absence of
  receiver
- Methods: `func (receiver Type) name(` -- extracted with method name only
- Structs: `type Name struct`
- Interfaces: `type Name interface`
- Constants: `const Name` (single and grouped)
- Variables: `var Name`

**Visibility convention**: Go uses capitalization for visibility -- names
starting with uppercase are public, lowercase are private. The provider
correctly applies this convention rather than relying on keywords.

**Build system**: `GoBuildSystem` detects `go.mod` files, parses module
paths, and identifies build targets.

**Known limitations**:
- Cannot parse function types (`type Handler func(...)`)
- Cannot distinguish between method sets and embedded interfaces
- Generated code (from `go generate`) may contain patterns the heuristic
  misses
- Build tags (`//go:build`) are not evaluated

## Cross-Language Symbol Mapping

The uniform `SymbolKind` mapping enables cross-language analysis:

| Construct | Rust | TypeScript | Go | SymbolKind |
|-----------|------|-----------|-----|-----------|
| Functions | `fn` | `function` | `func` | `Function` |
| Data types | `struct` | `class` | `type struct` | `Struct` |
| Contracts | `trait` | `interface` | `type interface` | `Trait` |
| Constants | `const` | `const` | `const`/`var` | `Const` |
| Type aliases | `type` | `type =` | `type` | `Type` |
| Namespaces | `mod` | -- | -- | `Module` |
| Implementation | `impl` | -- | -- | `Impl` |
| Enumerations | `enum` | `enum` | -- | `Enum` |

This means the graph, fingerprint, and search layers treat all symbols
uniformly. A Rust `trait` and a Go `interface` both produce
`SymbolKind::Trait` nodes, enabling cross-language structural comparison
via HDC fingerprints.

## Adding a New Language Provider

Adding support for a new language (e.g., Python) requires:

1. Create `crates/roko-lang-python/` with a `PythonLanguageProvider`
   implementing the `LanguageProvider` trait
2. Implement `parse_imports()` for Python's `import` and `from ... import`
   statements
3. Implement `extract_symbols()` for `def`, `class`, global assignments,
   and decorators
4. Map Python constructs to `SymbolKind`: `class` to `Struct`, `def` to
   `Function`, decorators to annotations
5. Optionally implement `BuildSystem` for pip/poetry/conda
6. Register the provider in the workspace index builder

The graph, fingerprint, search, and MCP server layers require zero changes.

## Future Tree-Sitter Providers

Tree-sitter grammars exist for TypeScript (`tree-sitter-typescript`) and
Go (`tree-sitter-go`). Implementing tree-sitter backends for these
providers follows the same pattern as the Rust tree-sitter provider:

1. Parse source with language-specific grammar
2. Walk named nodes to extract symbols (type-specific node kinds)
3. Walk `call_expression` nodes for call graph edges
4. Map language-specific visibility rules

The `LanguageProvider` trait interface remains unchanged -- the tree-sitter
backend is an internal implementation detail.

## Verified Behaviors

### Rust heuristic (39 tests)
- Function extraction (regular, async, unsafe, const, pub, pub(crate))
- Struct, enum, trait extraction with visibility
- Impl block extraction with trait names
- Import parsing (use, mod, extern crate, brace expansion)
- Angle bracket skipping for generics
- CargoBuildSystem workspace detection

### Rust tree-sitter (7 tests)
- Basic function, struct, enum extraction
- Impl block with `impl Trait for Type`
- Use import with brace expansion
- Parse error recovery
- Heuristic vs tree-sitter parity

### TypeScript (33 tests)
- ES module imports (named, default, star, type-only)
- CommonJS require
- Function, class, interface, enum extraction
- Export and export default handling
- NpmBuildSystem, PnpmBuildSystem, YarnBuildSystem detection

### Go (25 tests)
- Single and grouped imports with aliases
- Function and method extraction (receiver detection)
- Struct and interface extraction
- Visibility via capitalization
- GoBuildSystem go.mod detection
