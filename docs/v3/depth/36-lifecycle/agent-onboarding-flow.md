> Status: **Current** (`roko init` and `roko setup` wired; `roko doctor`
> validates workspace; `roko config providers discover` detects providers)

---

## 1. Purpose

The onboarding flow is the interactive experience that takes a user from
zero to a working roko workspace. It encompasses `roko init` (workspace
creation), `roko setup` (interactive wizard), `roko doctor` (health
validation), and provider discovery. The design principle is cognitive
simplicity: a user who has never heard of roko should have a working
workspace in under two minutes.

---

## 2. The Three Onboarding Personas

### New User

Has never used an agent framework. Arrives via documentation or
recommendation. Wants to "try an AI agent" without understanding the
infrastructure.

**Needs**: Template-based selection, minimal jargon, clear cost previews,
single-command deployment. Should never see `roko.toml` unless they go
looking.

**Experience**: `roko init --template rust-coding` produces a running agent
in under two minutes.

### Experienced User

Active developer or operator with existing infrastructure. Familiar with
agent frameworks. Wants automation for workflows they already execute
manually.

**Needs**: AI autofill from natural-language description, custom model
routing, tool profile customization, real-time cost estimation. Comfortable
reviewing generated `roko.toml` but does not want to write it from scratch.

**Experience**: `roko init --prompt "Monitor our staging cluster and alert on
anomalies"` produces a running agent in under three minutes.

### Developer / Institutional Operator

Runs self-hosted infrastructure. Wants full control: custom config files,
CI/CD integration, programmatic API access, multi-agent orchestration.

**Needs**: `roko init` to scaffold config, `--config` flag for
non-interactive deployment, `--dry-run` for cost preview, MCP config
passthrough.

**Experience**: `roko init --config ./production-agent.toml` deployed in
under sixty seconds.

## 3. `roko init` -- Workspace Initialization

The minimal entry point. Creates the `.roko/` directory structure and
generates a default `roko.toml`:

```bash
$ roko init

Created .roko/ directory structure:
  .roko/
  +-- state/
  +-- learn/
  +-- backups/
  roko.toml

Edit roko.toml to configure your agent, or run:
  roko setup          # Interactive setup wizard
  roko doctor         # Validate workspace health
```

The generated `roko.toml` contains annotated defaults:

```toml
# roko.toml -- Agent configuration
# Generated by `roko init`

[agent]
name = "agent-V1StGXR8_Z5j"
prompt = "Describe what this agent should do"
mode = "self-hosted"

[inference]
default_model = "claude-haiku-4-5"
escalation_model = "claude-sonnet-4-6"
critical_model = "claude-opus-4-6"

[neuro]
path = ".roko/neuro/"
max_signals = 50000
decay_model = "ebbinghaus"

[mesh]
enabled = false

[tools]
profile = "standard"
```

## 5. Provider Discovery

`roko config providers discover` scans for available LLM providers by
checking environment variables and common API key locations:

```bash
$ roko config providers discover

Discovered providers:
  anthropic     ANTHROPIC_API_KEY         claude-haiku-4-5, claude-sonnet-4-6, claude-opus-4-6
  openai        OPENAI_API_KEY            gpt-4o, gpt-4o-mini
  cerebras      CEREBRAS_API_KEY          llama-3.3-70b
```

Provider health is tracked at runtime. The `roko config providers health`
command shows live status, latency, and error rates for each configured
provider.

## 6. Domain Detection

When `roko init` runs in a directory with recognizable project structure,
it suggests appropriate domain configuration:

```bash
$ cd my-rust-project && roko init

Detected project type: Rust workspace (39 crates)
Suggested configuration:
  domain = "coding"
  language = "rust"
  workspace_path = "."

Apply suggested configuration? [Y/n]
```

Detection heuristics:
- `Cargo.toml` at root -> Rust workspace.
- `package.json` at root -> TypeScript/JavaScript.
- `go.mod` at root -> Go module.
- `foundry.toml` or `hardhat.config.*` -> Chain domain.
- Multiple language markers -> asks user to choose.

## 7. `roko doctor` -- Health Validation

The doctor command validates workspace health without modifying files:

```bash
$ roko doctor

Workspace Health
================
  [ok] roko.toml found and valid
  [ok] .roko/ directory structure intact
  [ok] Knowledge store path writable
  [ok] Episode log path writable
  [ok] At least one provider configured
  [ok] Default model reachable
  [!!] Gate thresholds stale (last updated 14 days ago)
  [ok] Disk space: 45.2 GB free (minimum: 1 GB)

Overall: HEALTHY (1 warning)
```

Specialized doctor variants:

```bash
roko doctor disk       # Disk space, stale targets, worktrees
roko doctor network    # Provider reachability, mesh connectivity
roko config doctor     # Config-specific health
```

## 8. First-Run Experience

After `roko init` or `roko setup`, the recommended first-run experience:

```bash
# 1. Quick test: single prompt through the scaffold
roko run "Summarize what this codebase does"

# 2. If the test works, try the self-hosting workflow:
roko plan generate "Wire SystemPromptBuilder into runner"   # writes plans/<slug>/
roko run plans/<slug>
#    (or both in one step: roko run --plan "Wire SystemPromptBuilder into runner")

# 3. Watch progress:
roko dashboard

# 4. Check learning:
roko learn all
```

Each command provides contextual help if it fails. `roko run` with no
provider configured suggests `roko setup`. `roko plan run` with no plans
suggests `roko plan create`.

## 9. Non-Interactive Deployment

For CI/CD and automated deployments, `roko init` supports fully
non-interactive mode:

```bash
# From config file (all fields present = no prompts)
roko init --config ./production-agent.toml

# With environment variables
ROKO_AGENT_MODE=self-hosted \
ROKO_INFERENCE_DEFAULT_MODEL=claude-haiku-4-5 \
ANTHROPIC_API_KEY=sk-ant-... \
roko init

# Dry-run: validate without creating
roko init --config ./agent.toml --dry-run
```

Config validation (`roko config validate`) can be run as a CI step to catch
configuration errors before deployment.

## 10. Migration from Existing Workspaces

`roko config migrate` handles upgrading from older config formats:

```bash
$ roko config migrate

Detected roko.toml version: 0.8.0
Current version: 1.0.0

Migrations to apply:
  1. Rename max_engrams -> max_signals
  2. Add [neuro.demurrage] section with defaults
  3. Move [chain.korai] to [chain.tokens]

Apply migrations? [Y/n]
  [ok] All 3 migrations applied
  [ok] Backup saved to .roko/config-backup-2026-09-15.toml
```

The E42 config evolution epic ensures migrations are safe, tracked, and
reversible via config profiles and merge tracking.
