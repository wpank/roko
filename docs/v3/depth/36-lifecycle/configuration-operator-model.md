## 1. Four Configuration Files

Agent configuration follows a four-file model with a strict override
hierarchy:

| File | Written by | Purpose | Hot-reloadable |
|------|-----------|---------|----------------|
| `roko.toml` | Operator | Infrastructure, inference, budget, knowledge, tools | Partial |
| `STRATEGY.md` | Operator (or AI autofill) | Agent goals, tactics, risk bounds | Yes (full) |
| `PLAYBOOK.md` | Agent (via Dream integration) | Machine-evolved heuristics from experience | Read-only to operator |
| Mesh config | Agent (via coordination) | Peer discovery, gossip topology | Read-only to operator |

The operator writes `roko.toml` and `STRATEGY.md`. The agent writes
`PLAYBOOK.md` and mesh configuration. This separation ensures that the agent
maintains genuine autonomy within operator-defined bounds.

## 2. `roko.toml` -- Infrastructure Configuration

The primary configuration file. Operator-authored, version-controlled, merged
from four sources in priority order:

```toml
[agent]
name = "agent-V1StGXR8_Z5j"
prompt = "Describe what this agent should do"
mode = "self-hosted"

[inference]
default_model = "claude-haiku-4-5"
escalation_model = "claude-sonnet-4-6"
critical_model = "claude-opus-4-6"

[neuro]
path = ".roko/neuro/"
max_signals = 50000
decay_model = "ebbinghaus"

[neuro.tiers]
transient_multiplier = 0.1
working_multiplier = 0.5
consolidated_multiplier = 1.0
persistent_multiplier = 5.0

[mesh]
enabled = false

[tools]
profile = "standard"

[budget]
max_daily_inference_usd = 10.0
```

### Hot-Reload Scope

| Section | Hot-reloadable | Requires restart |
|---------|---------------|-----------------|
| `[agent]` | No | Yes (name, mode changes need reprovisioning) |
| `[inference]` | Yes | No (model changes take effect next turn) |
| `[neuro]` | Partial | `path` requires restart; limits and tiers are hot |
| `[mesh]` | No | Yes (connection changes need re-handshake) |
| `[tools]` | Yes | No (profile changes take effect next tool load) |
| `[budget]` | Yes | No (limit changes take effect immediately) |

### Config Loading Priority

Four sources, in descending priority:

1. **CLI flags**: `--model claude-opus-4-6` overrides everything.
2. **Environment variables**: `ROKO_INFERENCE_DEFAULT_MODEL=claude-opus-4-6`.
3. **TOML config file**: `roko.toml` at the specified path.
4. **Built-in defaults**: Hardcoded sane defaults in `roko-core`.

Secrets (API keys, wallet keys) are only accepted from environment variables,
keystore files, or interactive stdin prompts -- never from CLI flags or config
files. Shell history, process listings, and crash reports never contain key
material.

## 3. `STRATEGY.md` -- Agent Goals

The operator-authored strategy document. This is the human-to-agent
instruction surface:

```markdown
# Strategy: Code Review Agent

## Objective
Review pull requests for correctness, style, and security issues.

## Scope
- Rust crates in crates/ directory
- Focus on safety-critical code paths
- Flag any .unwrap() in production code

## Risk Bounds
- Max review time per PR: 30 minutes
- Escalate security findings immediately
```

`STRATEGY.md` is fully hot-reloadable. Changing the strategy file sends a
"steer" signal to the cognitive loop, which picks up the new strategy on its
next planning cycle. No restart needed.

---

## 4. `PLAYBOOK.md` -- Machine-Evolved Heuristics

Written exclusively by the agent's Dream consolidation cycle. Contains
procedural knowledge distilled from experience. The operator can read
`PLAYBOOK.md` but cannot modify it -- this is the agent's learned knowledge:

```markdown
# Playbook (auto-generated by Dream integration)

## Heuristic: Gas Timing
- Optimal rebalance window: 02:00-06:00 UTC (lowest gas)
- Confidence: 0.87
- Validated: 147 observations over 3 weeks
```

## 5. Operator Freedom Hierarchy

The operator has five levels of control, from least to most disruptive:

### Level 1: Steer (Non-Disruptive)

Edit `STRATEGY.md`. The agent picks up the new strategy on its next planning
cycle. No interruption to current work.

### Level 2: Constrain (Bounded Disruption)

Modify `roko.toml` hot-reloadable sections. Changes take effect immediately
but do not interrupt in-progress work. Example: reduce budget limits, change
model routing, adjust tick intervals.

### Level 3: Pause (Reversible Disruption)

Suspend the cognitive loop. The agent stops processing but retains all state.
Resume restores the agent to its pre-pause state.

```bash
roko plan pause     # Suspend cognitive loop
roko plan resume    # Resume from where it left off
```

### Level 4: Restart (State-Preserving Disruption)

Stop and restart the agent process. Knowledge state is preserved on disk. The
agent resumes from its last persisted state. Required for config changes that
cannot be hot-reloaded (mesh URL, network, agent name).

### Level 5: Kill (Irreversible)

Immediately terminate the agent. Resources released. Knowledge state preserved
on disk (not destroyed). The user can later back up the knowledge and create
a new agent.

```bash
roko agent delete --name my-agent           # Clean shutdown
roko agent delete --name my-agent --force   # Immediate kill
```

## 6. Operator Responsibilities

The operator IS responsible for:

1. **Strategy definition** -- what the agent should do.
2. **Resource allocation** -- how much the agent can spend.
3. **Model selection** -- which LLMs the agent uses.
4. **Tool access** -- which tools are available.
5. **Coordination policy** -- whether the agent shares knowledge with others.
6. **Lifecycle management** -- when to create, pause, restart, delete.

The operator is NOT responsible for:

1. **Tactical decisions** -- the agent decides how to execute the strategy.
2. **Knowledge management** -- the agent manages its own knowledge via
   Ebbinghaus decay.
3. **Behavioral adaptation** -- the affect engine adjusts states based on
   performance.
4. **Consolidation scheduling** -- the Dream subsystem decides when to
   consolidate.

This separation prevents proletarianization (Stiegler 2010, 2018): an agent
that merely executes operator instructions without developing its own
understanding has lost the capacity for genuine knowledge. The operator sets
goals; the agent develops competence.

## 7. Configuration Validation

All configuration changes are validated before application:

- Budget can only increase with explicit confirmation (prevents accidental
  runaway costs).
- Model changes are always allowed but logged.
- `neuro.path` changes require restart (returns `ConfigError::RequiresRestart`).
- Unknown keys are rejected, not silently ignored.

The E42 config evolution epic (8/8) added seven config invariants,
priority/provenance tracking, migrations, merge tracking, profiles,
transactional reload, and freshness/doctor diagnostics.

## 8. MCP Config Passthrough

Roko supports Model Context Protocol (MCP) configuration passthrough:

```toml
[agent]
mcp_config = "/path/to/mcp-config.json"
```

The MCP config is passed to the agent dispatch layer, enabling integration
with external MCP servers for tool augmentation. Definition-only MCP
advertisements fail closed.
