# 64 — Model Discovery UX

**Priority**: P3 — Users cannot tell what models are available or what they can do without reading TOML files
**Size**: S (1–2 days)
**Crates**: `crates/roko-cli` (primary: `commands/config_cmd.rs`, `commands/util.rs`, `main.rs`), `crates/roko-core` (`config/model_registry.rs`, `config/provider.rs`)
**Depends on**: None

---

## Background

Roko maintains a compile-time registry of 13 well-known models (`BUILTIN_MODELS` in `roko-core/src/config/model_registry.rs`) and 13 common aliases (`ALIASES`). Each `BuiltinModel` entry carries `context_window`, `max_output`, `supports_tools`, `supports_vision`, `supports_thinking`, and `api_key_env`. The HTTP route `GET /api/models` already exposes capabilities and cost fields. None of this reaches the CLI user.

The current `roko config models list` output has four columns — Model, Provider, Slug, Key — and omits every capability flag, context window, aliases, and pricing. A user cannot answer "which models support vision?", "what is the context window on Gemini Pro?", or "what short alias can I use for claude-opus-4-6?" without grepping source files. The `roko config models route <model>` subcommand requires knowing a model name in advance, creating a chicken-and-egg problem.

Shell completions (`roko completions bash/zsh/fish`) are generated by `print_completions()` in `commands/util.rs`. The `dynamic_completion_words()` function scans `plans/` and `.roko/prd/` for filenames, but never emits model names. Typing `roko run --model <TAB>` produces nothing. The `--names-only` flag on `config models list` (which prints one slug per line) was designed for completion use but is never wired into the completion scripts.

When `--model claud-opus` is passed and fails to resolve, the error message says "unknown model" with no suggestions. The `builtin_model()` function in `model_registry.rs` returns `None` silently.

## Implementation Plan

### Step 1: Add a Capabilities column to `config models list`

Extend `ModelsListRow` in `crates/roko-cli/src/commands/config_cmd.rs`:

```rust
struct ModelsListRow {
    model: String,
    provider: String,
    slug: String,
    key_status: String,
    ctx_window: String,   // e.g. "200K" or "1.0M"
    capabilities: String, // e.g. "T V R"
}
```

Populate from `BuiltinModel` for builtin rows (lines 792–806) and from `ModelProfile` for configured rows (lines 760–773). Use compact letter codes:
- `T` = `supports_tools`
- `V` = `supports_vision`
- `R` = `supports_thinking` (Reasoning)
- `C` = `supports_caching`
- `W` = web search (Perplexity `sonar*` models — check `provider_kind == PerplexityApi`)

Format `context_window` as `200K` for values < 1,000,000, `1.0M` for values >= 1,000,000.

Update `format_models_list_rows()` to include the two new columns. Add a legend after the table:
```
Capabilities: T=tools  V=vision  R=reasoning  C=caching  W=web search
```

### Step 4: Add `config models show <model>` subcommand

Add a new variant to `ConfigModelCmd` in `crates/roko-cli/src/main.rs`:

```rust
/// Show detailed information for a single model.
Show {
    /// Model key, slug, or alias.
    model: String,
    #[arg(long)]
    workdir: Option<PathBuf>,
}
```

Add a handler branch in the `ConfigCmd::Models` match in `crates/roko-cli/src/commands/config_cmd.rs`. Implement `cmd_model_show(workdir, model_name)`:

1. Try exact match in configured models (from loaded `roko.toml`).
2. Try `builtin_model(model_name)` (handles alias resolution automatically).
3. If not found, compute edit distance between `model_name` and all known slugs+aliases, print top 3 suggestions, return error.

Output format:
```
Model: claude-opus-4-6  (alias: opus, claude-opus)
Provider: AnthropicApi
Context window: 200,000 tokens
Max output: 32,000 tokens
Capabilities: tools=yes  vision=yes  reasoning=yes  caching=no
API key: ANTHROPIC_API_KEY (set)
```

For edit distance, a simple Levenshtein distance implementation is sufficient (or import `edit-distance` crate if it is already a dep; otherwise implement a 20-line version inline).

### Step 5: Wire model names into shell completions

In `dynamic_completion_words()` in `crates/roko-cli/src/commands/util.rs` line 1508, add a model name entry:

```rust
// Model names for --model flag completion
let mut model_names: Vec<String> = roko_core::config::model_registry::BUILTIN_MODELS
    .iter()
    .map(|m| m.slug.to_string())
    .collect();
for (alias, _) in roko_core::config::model_registry::ALIASES {
    model_names.push(alias.to_string());
}
// Also try to load configured model keys from roko.toml in cwd
if let Ok(config) = roko_core::config::loader::load_config_unified(std::path::Path::new(".")) {
    for key in config.models.keys() {
        model_names.push(key.clone());
    }
}
model_names.sort_unstable();
model_names.dedup();
result.push(("--model".to_string(), model_names));
```

The completion scripts (`print_bash_completions`, `print_zsh_completions`, `print_fish_completions`) already handle entries from `dynamic_completion_words()` in their `case "$prev"` blocks. Adding `--model` to the list means typing `roko run --model <TAB>` will produce completions.

### Step 6: Add fuzzy suggestions on unknown model error

Find the location in the dispatch path where `--model <name>` resolves. This is in the model routing / dispatch dispatch path. When `builtin_model(name)` returns `None` AND the name is not in configured models, add:

```rust
// Suggest closest matches
let all_names: Vec<&str> = BUILTIN_MODELS.iter().map(|m| m.slug)
    .chain(ALIASES.iter().map(|(a, _)| *a))
    .collect();
let mut scored: Vec<_> = all_names.iter()
    .map(|n| (levenshtein(name, n), n))
    .collect();
scored.sort_by_key(|(d, _)| *d);
let suggestions: Vec<_> = scored.iter().take(3).map(|(_, n)| n).collect();
eprintln!("error: unknown model '{name}'");
eprintln!("Did you mean: {}?", suggestions.join(", "));
```

The `resolve_requested_model_slug` function in `config_cmd.rs` (line ~915) is one candidate location. Alternatively, add the suggestion printing to `builtin_model()` or to a new `builtin_model_or_suggest()` wrapper.

## Acceptance Criteria

1. `roko config models list` output includes a `Ctx` column (e.g., `200K`, `1.0M`) and a `Capabilities` column (`T V R`, etc.) for every row.
2. `roko config models list` prints an Aliases section listing all 13 entries from `ALIASES`.
3. `roko config models list --verbose` prints per-model detail blocks with all `BuiltinModel`/`ModelProfile` fields.

6. `roko config models show opus` resolves the alias and prints complete model information including API key status.

8. `roko completions zsh` output includes a `--model)` case block with all model slugs and aliases.
9. `cargo test -p roko-cli` passes, including at least one unit test verifying the capability column output format.
